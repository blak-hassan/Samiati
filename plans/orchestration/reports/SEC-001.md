# SEC-001: backend authorization audit

Completed 2026-11-09. Read-only delegate report; no deployed exploit or live-service test was performed. The coordinator inspected the cited billing guards, handle-update path, draft/submit path, curation/release operations and upload-attachment checks before assigning the first fixes.

Read-only audit complete: **five confirmed findings** in the current checkout. No files changed, commands executing tests/builds were run, credentials accessed, or live services contacted. Confidence is high from static call-path inspection; deployed behavior remains untested.

Coverage included Clerk identity resolution, guest handling, user mutations, chat/feedback callers, Changa claims/submissions/consent/validation, storage attachment, processing/curation, and billing/quota boundaries.

1. **High — Anonymous callers can read and cancel another account’s subscription.**

   **Locations:** [billing.ts:12](C:/Users/pc/Documents/samiati-1.0/convex/payments/billing.ts:12), [billing.ts:75](C:/Users/pc/Documents/samiati-1.0/convex/payments/billing.ts:75), [billing.ts:221](C:/Users/pc/Documents/samiati-1.0/convex/payments/billing.ts:221).

   **Path/trigger:** With a known user ID, call public `getActiveSubscription({userId})` without authentication; it returns the subscription ID and stored billing references. Then call `cancelSubscription({subscriptionId})`. Neither endpoint checks identity or ownership. The mutation marks the subscription canceled and writes a billing event. `getBillingHistory` likewise permits cross-account reads.

   The legitimate caller, [SubscriptionManager.tsx:37](C:/Users/pc/Documents/samiati-1.0/src/components/SubscriptionManager.tsx:37), supplies the current account’s IDs, but this UI convention does not constrain direct API callers.

   **Expected:** Account-scoped billing access requires the authenticated owner. Provider-side cancellation or financial effects were **not** established.

   **Smallest fix / owner:** Account & Settings: resolve `getCurrentUser`, require matching `userId`/`subscription.userId`, and apply equivalent guards to public account-scoped usage queries in `convex/payments/usage.ts`. No schema change; signatures can remain compatible.

   **Regression:** Anonymous and account B cannot read/cancel A’s subscription or write its billing events; A can perform the intended operations.

2. **High — The public legacy draft path bypasses claim and versioned consent requirements.**

   **Locations:** [submissions.ts:173](C:/Users/pc/Documents/samiati-1.0/convex/changa/submissions.ts:173), [submissions.ts:259](C:/Users/pc/Documents/samiati-1.0/convex/changa/submissions.ts:259), [submissions.ts:418](C:/Users/pc/Documents/samiati-1.0/convex/changa/submissions.ts:418).

   **Path/trigger:** An authenticated member calls `createDraftSubmission` for an existing text task, omitting consent and any claim. The draft receives all-false consent and no policy version or consent record. Calling `submitSubmission` with a nonduplicate answer passes ownership/answer checks and reaches `runSubmissionChecks`, which can route it to peer review without checking consent.

   No current UI caller uses `createDraftSubmission`; it remains an exported public mutation. The current UI uses `claimTask → startClaimedSubmission`, whose stronger checks therefore do not protect this alternate entry point.

   **Expected:** Every submission entering review must satisfy the authoritative claim/task and consent contract.

   **Smallest fix / owner:** Changa & Feedback: retire/internalize the unused legacy mutation, and enforce valid consent records and claim provenance at final submission. Reuse `consent.ts`; preserve existing draft compatibility deliberately.

   **Regression:** Direct legacy calls, missing consent records, false training consent and invalid policy versions cannot enter review; the valid claimed flow still succeeds.

3. **High — Consent revocation does not prevent subsequent release approval or membership.**

   **Locations:** [consent.ts:192](C:/Users/pc/Documents/samiati-1.0/convex/changa/consent.ts:192), [curation.ts:146](C:/Users/pc/Documents/samiati-1.0/convex/changa/curation.ts:146), [evaluation.ts:125](C:/Users/pc/Documents/samiati-1.0/convex/changa/evaluation.ts:125).

   **Path/trigger:** Curate a consented submission, then have its owner call `revokeConsent`. Revocation marks the record revoked and submission withdrawn, but leaves the copied curated example unchanged. It remains in the candidate query; a moderator can approve it and call `addReleaseMember`, including a training split. Those operations never recheck source submission status or consent.

   This reaches the existing curation UI through [curation/page.tsx:35](C:/Users/pc/Documents/samiati-1.0/src/app/dashboard/curation/page.tsx:35). Actual external dataset export was not exercised.

   **Expected:** Revoked material must be excluded from future approval and release selection.

   **Smallest fix / owner:** Changa & Feedback: retire linked examples on revocation and add authoritative source/consent eligibility checks to approval and release membership. Files: `consent.ts`, `curation.ts`, `evaluation.ts`; coordinate a shared eligibility helper with finding 2.

   **Regression:** Revoke before and after curation/approval; all subsequent approval, export-status and release-member operations reject the material, including stale UI requests.

4. **High — Reviewers can attach another contributor’s uploaded recording to their own submission.**

   **Locations:** [validation.ts:136](C:/Users/pc/Documents/samiati-1.0/convex/changa/validation.ts:136), [submissions.ts:520](C:/Users/pc/Documents/samiati-1.0/convex/changa/submissions.ts:520), [submissions.ts:532](C:/Users/pc/Documents/samiati-1.0/convex/changa/submissions.ts:532).

   **Path/trigger:** Member B obtains A’s in-validation submission from `listValidationQueue`, then calls `getValidationBundle`, which returns asset documents containing `storageId`. B creates an owned audio draft and supplies A’s storage ID to `attachSubmissionAsset`.

   Attachment verifies B owns the **destination submission**, plus storage metadata, but never verifies ownership or prior attachment of the **storage object**. B can therefore submit A’s recording under B’s identity and consent. The normal reviewer caller is [ValidationRunner.tsx:67](C:/Users/pc/Documents/samiati-1.0/src/components/changa/ValidationRunner.tsx:67).

   **Expected:** Review access must not grant contribution ownership or authority to consent for another person’s recording.

   **Smallest fix / owner:** Changa & Feedback, with coordinator ownership of schema changes: establish a trusted user/submission binding during upload completion and require it during attachment; reject foreign reuse. Files: `files.ts`, `submissions.ts`, `useUploadFile.ts`, potentially `schema.ts`.

   **Regression:** B can review A’s recording but cannot attach its storage ID; B’s own verified upload succeeds. A’s revocation cannot be circumvented through B’s copied attachment.

5. **Medium — User sync permits handle collisions that break another user’s profile lookup.**

   **Locations:** [mutations.ts:228](C:/Users/pc/Documents/samiati-1.0/convex/users/mutations.ts:228), [queries.ts:64](C:/Users/pc/Documents/samiati-1.0/convex/users/queries.ts:64).

   **Path/trigger:** An existing authenticated user calls public `users.mutations.store` with another account’s handle. The update branch patches it directly; uniqueness checks run only during account creation. `getProfile({handle})` subsequently calls `.unique()` and throws because two accounts match.

   `UserSync` normally supplies a Clerk-derived handle, but the backend accepts arbitrary mutation arguments. This confirms targeted lookup denial, not account takeover.

   **Expected:** Handles remain unique across both creation and updates.

   **Smallest fix / owner:** Account & Settings: check the handle index before updating, excluding the current user. No schema/API change; existing duplicates require a separate coordinated repair.

   **Regression:** B cannot adopt A’s handle; unchanged self-sync and a unique rename succeed; concurrent attempts preserve uniqueness.

Existing protections that work in the inspected paths:

- User identity comes from the authenticated Clerk subject; client-supplied user IDs do not select the current user. Guest rows alone provide no authenticated identity.
- Submission reads/writes generally enforce ownership or moderator access. Moderator/admin grants are server-authorized.
- Claimed starts validate owner, expiry, explicit training consent and active policy version.
- Asset attachment enforces draft state, stored size/content-type limits and one audio asset; clients cannot supply processing evidence.
- Validation rejects self-votes and closed submissions and maintains one vote per reviewer/submission.
- Public AI actions authenticate and enforce shared per-subject hourly/daily counters; worker processing functions are internal.

Existing tests primarily cover helpers, privacy defaults and local history; they do not establish these authorization boundaries. Follow-up verification needs two member accounts, a moderator, an anonymous client, owned recordings and a seeded subscription. Clerk claim configuration, storage URL behavior after revocation, and paid entitlement enforcement require controlled execution; the current AI quota helper explicitly selects the free tier.
